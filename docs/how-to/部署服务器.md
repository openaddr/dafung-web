# 部署服务器

本手册供 VPS 维护者首次安装、更新和回滚联机服务器。部署工具以 root 管理 `dafung.service`，服务通过本机端口提供 HTTP 大厅与 WebSocket 对战。公网入口由运维者在 1Panel 管理。服务器设计见[联机架构](../explanation/联机架构.md)与 [ADR-0072](../adr/0072-workspace-packages-and-server-artifact.md)。

服务在一台 VPS 上运行一个进程。维护者选定维护窗口后执行命令，安装或切换随即开始。重启会断开现有连接。

## 从 WSL 部署

在 WSL 的 `~/.ssh/config` 配置 `dafung-vps`，将 `vps.example.com` 替换为 VPS 的 SSH 地址。按需添加 `IdentityFile` 指向能以 root 登录的密钥。换服务器时更新这个别名的 `HostName`，并核对新主机的 SSH 指纹。

```sshconfig
Host dafung-vps
    HostName vps.example.com
    User root
```

在项目根目录执行以下命令。预检会从当前工作树构建服务端归档，计算 SHA-256，并验证公钥登录和 VPS 上的 Bun 版本。

```bash
bun run deploy --dry-run
bun run deploy
```

`bun run deploy` 使用与 `bun run build:server` 相同的本地构建逻辑，发版号取自 `package.json`。命令以 WSL 的 SSH 公钥连接 `dafung-vps`，将刚构建的服务端包、摘要和安装器传到 VPS。安装器负责验包、切换版本并核对 `127.0.0.1:9981` 的本机健康状态。WSL 需要 Bun、已安装的仓库构建依赖、OpenSSH 和 GNU tar。VPS 可使用已经留存的 Bun，或从 `PATH` 找到归档指定的 Bun 版本。

命令失败时会报告中断的阶段、首条错误和 WSL 上的日志目录。需要排查 SSH 或安装器细节时，读取目录内的 `stdout.log` 和 `stderr.log`。

同发版号重新打包时，解包文件一致即可重启并恢复原房间。如果同发版号的运行文件已经变化，安装器会在停服前报出冲突文件。修改服务端内容后，先更新 `package.json` 的发版号。跨版部署会从空房启动。

## 准备安装

1. 选定同时带有服务端包和安卓 APK 的 GitHub Release。记下它的标签，取得 `dafung-server-<标签>.tar.gz`、该资产公布的 SHA-256 和 `<标签>-aarch64.apk`。记录 SHA-256 的 64 位十六进制值，去掉 GitHub 摘要里的 `sha256:` 前缀。
2. 在开发工作区生成独立部署工具。

   ```bash
   bun build scripts/deploy-server.ts --target=bun --outfile tmp/deploy-server.js
   ```

3. 将 `deploy-server.js` 和所选发布包复制到 VPS。VPS 需要 Linux、systemd、GNU tar 和该发布包 `release.json` 指定的 Bun 版本。部署命令使用本地文件，VPS 无需安装仓库依赖或配置 GitHub 凭据。

如果主机已按旧源码流程安装了 `dafung.service`，先安排停服并保留原配置、房间和日志，再撤除旧单元。部署工具遇到既有自定义单元会报错。

## 安装、升级与同版重启

在 VPS 上以 root 登录，把 `release_tag` 设为选定的发版标签，将 `release_sha256` 设为已取得的可信摘要。用该发布包要求的 Bun 路径执行。

```bash
"$(command -v bun)" ./deploy-server.js install \
  --tag "$release_tag" \
  --archive "./dafung-server-${release_tag}.tar.gz" \
  --sha256 "$release_sha256"
```

首次启动监听 `127.0.0.1:3000`，`--port <端口>` 可指定其他本机端口。后续安装省略 `--port` 时沿用当前端口。部署工具在停旧服务之前验证摘要、标签、Bun 版本、归档路径、地图清单和已编译的扩展入口。已解包的同标签目录须逐文件与原始归档一致，发现损坏时会报出路径并停止部署。

用同样的命令再次安装当前发版号，会重启服务并从原房间目录恢复。选用不同发版号会切到新建的空房间及日志目录，原目录留存。工具核对服务处于运行状态，并通过本机 `/health` 和 `/help` 核对监听配置、房间、日志、地图和扩展目录。切换失败时，工具尝试恢复原部署指针，重新启动原先运行的服务并检查其就绪状态。候选服务未能停止或原服务未能恢复时，工具会报告失败步骤。

```bash
curl --fail http://127.0.0.1:3000/health
journalctl -u dafung.service -n 50
```

如使用自定义端口，把检查地址和交给 1Panel 运维者的上游端口改成实际值。联机入口可用后，用同一发版号的两台安卓 APK 建房、加入、开局，见[联机对战](联机对战.md)。

## 回滚与普通卸载

```bash
"$(command -v bun)" ./deploy-server.js rollback
```

回滚到上一次部署选择的发布包、Bun、端口和配套房间、日志目录。工具会在停服前核验留存的发布包文件，被切下的部署及其数据仍留在磁盘。回滚后用对应版本的安卓 APK 验收联机。

```bash
"$(command -v bun)" ./deploy-server.js uninstall
```

卸载会停止、禁用并移除 systemd 单元，保留应用文件、配置、房间和日志。再次安装同一发版号可继续使用当前保留的房间。永久清除数据是独立操作。

## 配置与数据

| 路径                                  | 内容与用途                                 |
| ------------------------------------- | ------------------------------------------ |
| `/opt/dafung/releases/<标签>`         | 已核验发布包的解包目录                     |
| `/opt/dafung/runtimes/<Bun 版本>/bun` | 回滚时所需的 Bun 可执行文件                |
| `/opt/dafung/current`                 | 指向当前部署配套的发布包、运行时和数据配置 |
| `/etc/dafung/app.env`                 | 操作员管理的应用设置                       |
| `/var/lib/dafung/activations`         | 切换时生成的部署记录与当前部署的回滚信息   |
| `/var/lib/dafung/data/<目录>`         | 每次跨版切换对应的 `rooms/` 和 `logs/`     |
| `/etc/systemd/system/dafung.service`  | 部署工具管理的联机服务单元                 |

在 `/etc/dafung/app.env` 可设置 `LOG_TTL_DAYS`（默认 30 天）和 `DECISION_TIMEOUT_MS`（默认 120000 毫秒，0 关闭）。改动在重启时生效。监听地址、端口、房间、日志、地图和扩展目录由部署工具在最后读取的配置中固定。地图和扩展目录指向所选发布包。SSH 运维凭据单独管理。

对局日志按局写入 `<gameId>.jsonl`，保留期清扫在服务启动时运行，详见[对局日志](../reference/对局日志.md)。用 `GET /help` 的 `env` 字段核对实际配置，用 `GET /room/debug?room=<房间码>` 核对房间恢复和近期事件。启动时会在 journal 报告损坏房间、恢复数量和其他告警。

部署进程若被强制中断，先确认该进程已退出，用 `systemctl status dafung.service`、`readlink /opt/dafung/current` 及本机健康检查确认停在何处。确认没有进程操作部署后可用 `rmdir /var/lib/dafung/.deploy-lock` 解除遗留锁，再重试部署或回滚。
