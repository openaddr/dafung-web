# 部署服务器

面向维护者:把联机服务器部署到一台 VPS 并日常发版。服务器设计动机与决策索引见[联机架构](../explanation/联机架构.md)。

## 认清拓扑

一台 VPS 两件套,对外只暴露一个域名:**Caddy**(:443)自动签发续期 Let's Encrypt 证书,HTTPS / WSS 反代到本机端口(WS upgrade 自动透传,免配 header);**应用**由 systemd 守护 `bun scripts/server.ts`(默认 :3000)——REST 大厅 + WebSocket 对战 + 同进程静态托管 `dist/`,网页与对战同源,客户端 `serverUrl = location.origin` 免填地址。免填仅适用网页通道(开发与 AI 测试用):APK 的 WebView 自带 origin 是 `tauri://localhost`,上面没有引擎——真机联机须在大厅「高级(服务器地址)」显式填本域名,存 localStorage 后有记忆。

## 运维约定

- 正式联机服务在单台 VPS 上运行一个服务端进程。需要重启时安排维护窗口，允许短暂停服。
- 按 Git 发布标签部署服务端，并使用同一发版号的安卓 APK 验收联机。发版号单源见[文档规约](文档规约.md#发版)。
- 普通卸载撤除联机服务，保留应用配置、房间文件和对局日志。永久清除这些数据是独立操作。

## 首次部署

### 备好服务器与域名

- 一台 VPS(下文以 `<你的 VPS>` 指代)与一个域名,域名 A 记录指向 VPS 公网 IP;VPS 上装 Bun(`bun --version` ≥ 1.3,原生跑 TS 无转译依赖,见 ADR-0009)与 Caddy 2。
- ⚠️ 域名是 `.cn` 且 VPS 在国内:对外提供 Web 需 ICP 备案,否则 80/443 可能被拦截;海外机器不受限。
- 下文的 `dafung.openaddr.cn` 是示例。Caddy 站点、健康检查和 APK 服务器地址统一填实际域名。

### 拉代码并构建

将所选 Git 发布标签与 Git 仓库地址分别赋给 `release_tag` 和 `repo_url`。

```bash
git clone --branch "$release_tag" "$repo_url" /opt/dafung-web
cd /opt/dafung-web && bun install --frozen-lockfile && bun run build
```

### 写应用 env

建 `/opt/dafung-web/.env.app`(**与 SSH 凭据的 `.env` 是两份文件**,见「做日常运维」末条),只写与默认值不同的项;走反代时 `HOST` 收 `127.0.0.1`,应用端口只听回环、外网摸不到。全部变量见下文 env 表:

```
PORT=3000
HOST=127.0.0.1
```

### 装成 systemd 服务

首次安装时创建系统用户及组 `dafung`，例如 `sudo useradd --system --user-group --no-create-home dafung`。确保服务用户可读应用目录并可写 `ROOMS_DIR`、`LOGS_DIR`。使用默认路径时，先创建 `data/rooms` 和 `data/logs` 并将这两个目录交给该用户。核对 `ExecStart` 中的 Bun 路径与 VPS 实际安装位置一致。

`/etc/systemd/system/dafung.service`:

```ini
[Unit]
Description=dafung-web multiplayer engine
After=network.target
[Service]
Type=simple
User=dafung
WorkingDirectory=/opt/dafung-web
EnvironmentFile=/opt/dafung-web/.env.app
ExecStart=/usr/local/bin/bun scripts/server.ts
Restart=on-failure
[Install]
WantedBy=multi-user.target
```

### 配 Caddy 反代

`/etc/caddy/Caddyfile`(站点块写真实域名,Caddy 自动签证书):

```
dafung.openaddr.cn {
    reverse_proxy 127.0.0.1:3000
}
```

### 启动并验证

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now caddy dafung
curl --fail https://dafung.openaddr.cn/health    # 期望 {"ok":true,"uptime":...,"rooms":...}
```

再做真实冒烟:两台安卓设备安装当前 APK,在大厅「高级(服务器地址)」均填入 `https://dafung.openaddr.cn`;一台建房,另一台用房间码加入,开局走几手(玩法见[联机对战](联机对战.md))。

## 升级与回滚

1. 选定目标发布标签，在独立目录检出并执行 `bun install --frozen-lockfile && bun run build`。构建成功后再切换。
2. 在维护窗口内停止 `dafung`。保留上一版部署目录和 systemd 单元，备份应用配置、房间目录和对局日志目录，注明原发版号和备份时间。
3. 准备新版应用配置，将对局日志复制到新版的日志目录。跨版本无兼容承诺。需要尝试续局时使用旧房间目录的副本，需要清盘时为新版指定空房间目录。
4. 将 systemd 单元的 `WorkingDirectory` 和 `EnvironmentFile` 指向新版，确认服务用户对数据目录有写权限，再执行 `systemctl daemon-reload` 并启动。查询 `/health`，检查启动日志中的房间恢复情况，再用同一发版号的两台安卓 APK 建房、加入、开局。

验收失败时停止新版，切回上一版服务单元、应用配置及停服时的数据目录，再加载单元、启动并用上一版 APK 验收。新版运行期间产生的文件单独留存。

启动时，无法读取或解析的房间文件会告警并保留。房间恢复时抛错会告警、尝试删除对应快照，再继续恢复其他房间。`/health` 只报告进程存活、运行时长和房间总数。查看启动日志的恢复数量和告警，用 `/room/debug?room=<房间码>` 核对需要保留的房间。

## 卸载

1. 停止并禁用 `dafung`，将应用配置、`ROOMS_DIR` 和 `LOGS_DIR` 归档到部署目录之外。
2. 移除 `dafung.service` 和本服务的部署目录，执行 `systemctl daemon-reload`。从 Caddy 中移除本服务的站点块，校验并重新加载 Caddy 配置。
3. 检查 `dafung` 已停止、站点已撤除且归档文件可取用。确需永久清除时，单独确认并删除对应归档。

## 配置环境变量

全部可缺省(默认值即下表);相对路径按 systemd `WorkingDirectory` 解析为绝对路径。变量名与源码常量同名,出处列即定义所在文件:

| 变量                  | 默认值           | 用途                                                                      | 出处                                               |
| --------------------- | ---------------- | ------------------------------------------------------------------------- | -------------------------------------------------- |
| `PORT`                | `3000`           | HTTP + WS 监听端口                                                        | `scripts/server.ts`                                |
| `HOST`                | `0.0.0.0`        | 监听地址;源码默认全网卡(局域网直连),走反代建议 `127.0.0.1`                | `scripts/server.ts`                                |
| `ROOMS_DIR`           | `./data/rooms`   | 房间落盘目录:`<房间码>.json` + `<房间码>.events.jsonl`,启动自动创建并恢复 | `scripts/server.ts`(`scripts/room-persistence.ts`) |
| `STATIC_DIR`          | `./dist`         | 静态托管目录;缺目录时接口报「先 `bun run build`」                         | `scripts/server.ts`                                |
| `LOGS_DIR`            | `./data/logs`    | 对局日志 `<gameId>.jsonl`(ADR-0014)                                       | `scripts/server.ts`                                |
| `LOG_TTL_DAYS`        | `30`             | 启动清扫:mtime 超此天数的 `.jsonl` 删除                                   | `scripts/server.ts`                                |
| `DECISION_TIMEOUT_MS` | `120000`(`0`=关) | 决策停摆看门狗:真人座位超时未落子自动托管(ADR-0028)                       | `scripts/server.ts`                                |
| `STATE_FILE`          | —                | **已废**:旧文档名,现源码不读;房间目录用 `ROOMS_DIR`                       | —                                                  |

## 做日常运维

- **看健康状况**:`curl /health`(存活/运行时长/房间数);排障加 `GET /room/debug?room=<房间码>`(实时相位 + 事件尾巴);当前生效的 env 值 `curl /help` 看 `env` 字段。
- **管日志**:对局日志按局写 `data/logs/<gameId>.jsonl`,每手增量追加;TTL 清扫只在**启动时**跑一次,改 `LOG_TTL_DAYS` 需重启生效;归档口径见[对局日志](../reference/对局日志.md)。
- **看房间**:`data/rooms/` 里的房间(含进行中对局)重启自动恢复;损坏的房间文件启动时跳过并 `console.warn`,不拖垮其余房间。
- **分清两份 env**:服务器上的 `.env`(`server_ip` / `server_pwd` 等)是**你自己的 SSH 运维凭据,应用不读**;应用 env 是 systemd `EnvironmentFile` 指向的 `.env.app`,别把运维凭据混进去。
