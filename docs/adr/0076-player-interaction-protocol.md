# ADR-0076 局内玩家交互协议

2026-11-27 接受以下设计，待实施。

安卓界面和未来通过 MCP 入座的无界面玩家共用一份协议。协议描述一个座位想做什么，以及这个座位在操作前后可以观察到什么。更换渲染器时可以复用交互逻辑，更换规则引擎时可以用同一组对局场景验证行为。

## 玩家意图与草选

点沙盘上的吴国棋子和点吴国席位都表达「选择吴为目标」。打开吴的诸侯详情表达「查看吴」的查询意图。渲染器把触点解释为意图，并负责排版和高亮。独立于渲染器的交互逻辑接收意图，依据本座位的选项集校验草选，返回已选对象和当前可执行的操作。房间收到改变对局的命令后，校验座位、阶段和目标，由权威引擎执行。玩家通过协议得知处理结果、拒绝原因及后续可做的操作。[选项集决策](./0013-choice-set-and-auto-execute.md)与[事件流决策](./0020-event-stream-sync-model.md)分别说明选项和局面变化的来源。

单机开局、联机重连和局内更新都由控制器发布一致的座位视图。首连和重连从座位摘要恢复，日常局面由收到的事件批推进。玩家从同一份视图读到当前公开局面、本席能否操作、有哪些选择和已经选中了什么。安卓据此绘制高亮和按钮，无界面玩家据此选择下一步。

蜀使用「连环计」时，点亮吴是蜀的草选。「下一步」获房间接受后，吴成为已确认的第一位，蜀可在第二步返回改选。重新进入对局时，由房间恢复仍然有效的已确认步骤。只点亮吴就退出的玩家可以重新选择。两步都合法并最终出牌时才消耗一张连环计。见[出牌与选目标规则](../reference/rules/06-锦囊.md)。

持牌座位能逐张指认同名锦囊。从左到右持有「连环计、火烧连营、连环计」时，选择最右一张，进入选目标或返回改选时只有这张牌显示为已选。最终从手中移走右边这张，剩余牌序为「连环计、火烧连营」。

## 重复提交与迟到指令

玩家提交抉择时，每一笔都对应发起它的房间、座位和决策点。房间处理过这笔提交后，原座位断线重连再发同一笔，取得首次受理或拒绝的结果及相应原因。玩家有两张连环计时，第一笔出牌重发仍只消耗一张，主动打出另一张是新的一笔。重连后的局面取当前座位摘要，军情密探的牌面仍随当次生效事件交付。现有请求编号用于配对诊断回执，这项设计还要求房间能够识别已处理的提交。见[命令回执与重连](../explanation/联机架构.md)。

如果这是房间第一次收到该提交，权威校验原决策点是否仍对本座位有效。第一轮识破的应答在第二轮才首次到达，即使这一席在第二轮也能打出识破，房间仍应返回原窗口已结束的原因，保留牌和本轮应答机会。连环计点过「上一步」并改选后，先前第二步的提交也会失效。拒绝后，玩家可以根据当前座位视图继续操作。

联机房间将这笔提交的处理结果与相应局面变更一起持久化，再向发起座位确认。回执保留期跟随可恢复的房间。若扣牌已落盘、回执尚未送达时服务器重启，恢复同一房间后，原座位重发应取得原结果，扣牌仍只有一次。若上次提交被拒绝，也能取回原拒绝原因。现有恢复入口见[房间持久化](../../packages/core/src/room/room.ts)和[恢复用例](../../test/online/room-recovery.test.ts)。

## 座位可见性

单机、联机和无界面玩家都按座位取得局面、选项集、操作结果和事件。吴通常只知道魏有几张锦囊，魏当前能打出的牌和未公开的目标只给魏。若吴的「军情密探」生效，魏的牌面只在这次窥探中交付给吴。这些限制在数据交给玩家接口前生效。

此决定修订了此前允许单机界面隐藏暗牌的做法。目前单机首连会取得完整快照，联机座位快照在裁掉他人的手牌后仍带有行动者的出牌选项和待选锦囊。接入玩家协议时，两处都需要按接收座位交付数据。见[原决策 ADR-0016](./0016-per-seat-snapshot-redaction.md)、[房间首连](../../packages/core/src/room/room.ts)和[座位投影](../../packages/core/src/room/seat-projection.ts)。

## 引擎替换的行为验收

从相同开局给出相同的玩家意图、随机结果和超时先后。在每个决策点核对各座位可见的局面、可选操作、拒绝原因和结算结果。第一目标已确认吴时，再提交吴为第二目标应被拒绝，手牌张数和选择步骤保留。改交合法的第二目标后只扣一张牌。即使终局银两相同，途中遗漏了返回改选或识破的机会，这个场景也应判为失败。

专用测试房允许测试工具统一推进整间房的时钟，玩家端通过正常的座位接口观察期限并作答。用同一局面分别验证 AI 在截止前主动打出「识破诡计」，以及测试工具推进到截止后由房间按「不用」处理。两种结果都经过权威规则结算。日常对局使用真实时间。

## 首批交付

先让现有安卓界面和一个不加载 React 的无界面玩家，分别用同一协议在真实房间打完连环计。以蜀按顺序持有「连环计、火烧连营、连环计」开场，同时检查另一座位通过玩家接口实际收到的数据。

| 场景                                                                     | 应观察到的结果                                                             |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 选中手牌中靠右的连环计，确认第一目标后重连，再返回改选                   | 操作席位从已确认步骤继续，选中的仍是右边这张，另一席只收到按规则公开的信息 |
| 重新进入第二步，提交先前第二步发出但迟到的指令，再用当前步骤提交非法目标 | 两笔均给出相应拒绝原因，手牌张数与当前应有的选择机会保留                   |
| 合法提交第二目标，房间保存结果后在回执送达前重启，原座位重发             | 取回原受理结果，只结算一次，手牌依序剩下「连环计、火烧连营」               |

现有的[连环计接线用例](../../test/wiring/jinnang-wiring.test.tsx)和[房间下行用例](../../test/online/local-hydration.test.ts)覆盖了部分路径。

这条流程验通后，MCP 接入同一玩家接口。其余锦囊、珍宝、名将等局内操作按同一约定逐步接入。
