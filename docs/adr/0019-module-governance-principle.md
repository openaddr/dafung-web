# 模块代码治理:单一主题、具体命名、委托式拆分

源码文件的模块划分按本原则常设执行,目的:**可读性、维护性、扩展性**。起因:`game.ts` 涨到 3808 行(占 core 层 46%)。全面盘点(决策见 tracker「全仓大文件职责盘点」)证明它不是纠缠的意面,而是「没切分的整齐文件」——8+ 个机制域只经公共底座交互、域间零私有互调,切缝现成;治理规则借此沉淀为常设原则,防下一次长回来。

**条款:**

1. **单一主题可命名**:每个源文件必须能用一个具体领域词命名并说清自己管什么;笼统聚合桶(game/utils/helpers/misc/types 式命名)禁止——文件名笼统,人和 AI 都会往里塞东西。词汇表(GLOSSARY.md)`_Avoid` 词不上文件名;既有例外明示:`server.ts` 为进程入口惯例保留,`gameLog*` 由「对局日志(Game Log)」背书。
2. **行数是症状不是病**:参考带=同类核心流程 700–900 行(boardgame.io `flow.ts` 921)、工具默认 300–1000(ESLint/SonarQube);超 1000 必须有单一主题的明示理由。不设硬阈值,不为凑数强拆出假模块。
3. **拆分模式**:机制域为轴;域逻辑=自由函数(直接读写引擎状态字段);引擎类保留公共方法名做 1–3 行薄委托,外部 importer 无感。模块边界=文件边界,不做访问控制(零兜底:内部状态透明)。类型随域走,不留聚合桶(`types.ts` 解散)。
4. **变更纪律**:搬运与改名分离——一次 diff 只做一类变更;搬运票以「测试网全绿 + 同种子整局快照哈希不变 + 公共方法清单 diff 为零」机械自证;改名走独立小票、调用点机械跟随。唯一不可让项=引擎行为不变。
5. **壳纪律**:引擎壳(`authority.ts`)只含状态字段、构造器、薄委托、命令路由、快照通道;行数上限与机制域禁入由 `scripts/check-core-purity.ts` 断言强制——**治理靠门禁,不靠自觉**。

放弃了三个替代:接受大文件(维护成本随行数超线性增长);按技术层或相位拆(切线会切穿函数体,`marchTraverse` 单函数 108 行横跨多相位即是证);硬性行数阈值(制造为拆而拆的假模块)。

后果:拆分施工按 tracker「模块治理施工总览」的 11 票序列执行(每票一 PR);`check-core-purity.ts` 增加壳纪律断言;新增文件命名与拆分模式以本 ADR 为验收依据。
