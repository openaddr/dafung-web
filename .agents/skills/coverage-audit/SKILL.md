# 覆盖率体检(coverage-audit)

低频体检,不是日常门禁。基线很好(2026-09-13 core 几乎全绿,见台账),本 skill 的职责是**守住基线**,不是刷高数字。

## 何时执行(刻意低频)

1. 用户明说:"查覆盖率" / "覆盖率体检" / "coverage"
2. 大型 core 重构合入后(如 game.ts 拆分)——验证测试网没被手术撕开
3. 发版打 tag 前
4. 台账最新一条距今 ≥1 个月,且期间有较大 core 改动 → 可向用户提议跑一次

不在以上情形时不要跑。

## 怎么做

1. `bun test --coverage`——bun 内建,零配置,终端直接出每文件表(%行 / %分支 / 未覆盖行号)。
2. 只看三类东西:
   - **从基线掉下来的文件**:core 基线几乎全绿,任何掉落都值得问一句为什么;
   - **core 关键域的薄弱段**:game.ts 私有结算/破产/锦囊段、encounters、effects/timing 派发;
   - **与台账上一条的 diff**:上次标记的缺口补了没;新改动静出的新盲区。
3. 登记 `docs/reference/覆盖率台账.md`:新起一节,写日期、基线对照结论、薄弱点与处理建议。文件不存在则按既有格式创建。
4. 向用户报告**值得行动的发现**,不逐文件念表。

## 判读口径

- **app/ UI 层大量 0% 是正常态**:DOM/three.js/Web Audio 跑不进单测,该层由 e2e 兜,覆盖率无诊断价值——不要为此补测试。
- `theme.ts` 行覆盖低但分支覆盖高:数据表文件,正常,不管。
- `scripts/fetch-asset.ts`、`engine-helpers.ts` 覆盖低:网络工具/CLI 专用路径,按需评估,非体检重点。
- 体检重点只有一块:**`src/core/`**。

## 红线

- 不设阈值、不进 CI 红绿门(覆盖率进 CI 只会教人刷数字)
- 不为刷百分比写测试;补测优先级 = 域重要性 × 缺口大小
- 不引入 lcov/HTML 报告工具——终端表就是全部
