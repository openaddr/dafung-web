# 覆盖率体检(coverage-audit)

低频体检,不是日常门禁。以核心规则风险为目标,当前测量与历史记录分开判读。

## 何时执行(刻意低频)

1. 用户明说:"查覆盖率" / "覆盖率体检" / "coverage"
2. 大型 core 重构合入后(如 authority.ts 拆分)——验证测试网没被手术撕开
3. 发版打 tag 前
4. 台账最新一条距今 ≥1 个月,且期间有较大 core 改动 → 可向用户提议跑一次

不在以上情形时不要跑。

## 怎么做

1. 按项目全量测试纪律运行一次 `bun test --coverage`,保留完整终端输出。记录 Bun/代码版本、运行范围、默认/慢池与跳过项。Bun 表头是 **% Funcs / % Lines**(函数/行覆盖率),未覆盖行用于定位;它不提供分支覆盖率。
2. 核对核心规则证据:
   - **同域可比的掉落**:先确认文件职责、语料和池范围一致;重构前后或运行范围不同的数字只作历史参考。
   - **关键状态路径**:按选都、行军、机遇、锦囊反应窗、珍宝交涉、清算等领域,关联正常、拒绝、中断与恢复的现有规则期望或真实缺口,无需展开全组合。
   - **薄弱段与历史发现**:从 `authority.ts` 委托的机制域文件、`effects.ts`/`timing.ts` 派发追查未命中代码;确认是有效规则缺口再补少量确定性用例。补测后若只跑定向,台账注明正式覆盖率在补测前取得,不重跑全量刷数。
3. 登记 `docs/reference/覆盖率台账.md`:覆写为最近一次测量的参考快照和判据指针,写明范围、适用性、证据与未决缺口。历史由 git 保留,不追加节、不维护用例计数;文件不存在则创建当前快照。
4. 向用户报告**值得行动的发现**,不逐文件念表。

## 判读口径

- **app/ UI 层按证据判层**:关键接线(happy-dom)守点击、命令与状态;视觉、手势和设备交互由用户在 APK 中验收。按 ADR-0065 不恢复浏览器回归,不按 UI 百分比机械补测。
- **证明范围分开**:固定种子证明确定性;黄金台账证明既有行为未漂移;规则期望证明具体结果;整局不变量只守登记的性质。它们均不替代用户在 APK 中的视觉与设备交互验收。
- `theme.ts` 是数据表,声明未命中不等于规则缺口,按数据与消费路径判读。
- `scripts/fetch-asset.ts`、`engine-helpers.ts` 覆盖低:网络工具/CLI 专用路径,按需评估,非体检重点。
- 体检重点只有一块:**`src/core/`**。

## 红线

- 不设阈值、不进 CI 红绿门(覆盖率进 CI 只会教人刷数字)
- 不为刷百分比写测试;补测优先级 = 域重要性 × 缺口大小
- 不引入 lcov/HTML 报告工具——终端表就是全部
