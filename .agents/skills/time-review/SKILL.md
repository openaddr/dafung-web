# 耗时分析(time-review)

对「我实现某个要求」的过程做真实耗时归因:一切结论来自 ZCode 本机落盘记录,不含估算与印象。数据源的字段细节、口径推导与基线账表见 [`docs/agents/耗时回顾.md`](../../../docs/agents/耗时回顾.md);仓库的验证命令与纪律条款分别在 [`docs/how-to/开发与测试.md`](../../../docs/how-to/开发与测试.md) 与 `AGENTS.md`(派单纪律/分层验证),推荐方案要挂到这些既有条款上。本页是可独立执行的通用流程。

## 输入

任务标识(如「锦囊 UI 一期」「上次那个重构」)。模糊时先圈定:用 `git log --date=format-local:'%m-%d %H:%M' --grep=<关键词>` 或分支名找提交簇,向用户确认起止后再动手。

## 流程(五步)

### 1. 定窗

- 提交簇首尾时刻圈定时间窗;**剔除窗内轮间离席**(轮与轮之间 >10min 的 gap 是日历不是工时,单独汇报不进耗时账——它常是「体感慢」的主因)。
- 轮次时间线:`~/.zcode/cli/log/zcode-YYYY-MM-DD.jsonl` 的 `turn.started/completed` 事件按 sessionId 过滤、**turnId 去重**(同轮触发多条)。

### 2. 取数(四源,各答一个问题)

| 源                                                   | 答                                                                                                                                            |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `~/.zcode/cli/log/zcode-*.jsonl`                     | 工具明细(`tool.call.completed`:toolName/durationMs/querySource)、模型请求(`model.request.completed`:durationMs + querySource 分流主线/子代理) |
| `~/.zcode/cli/rollout/model-io-sess_<id>.jsonl`      | 主线程逐次模型调用(completedAt/durationMs)——**压缩后重置**,只覆盖最近一段;相邻调用之差 = 工具执行/等待间隙                                    |
| `~/.zcode/cli/agents/<sessId>/agent_*/metadata.json` | 每个子代理真实墙钟(createdAt→completedAt)、tokens、工具数                                                                                     |
| `git log`(本地时区)                                  | 阶段边界与提交时刻                                                                                                                            |

### 3. 归因(三分法 + 遮盖算法)

- 轮内墙钟 = **子代理可见墙钟**(并行只算 max,被遮盖者单独注明)+ **主线模型时间**(rollout durationMs 求和)+ **等待**(≥60s Bash 逐条认领:e2e/build/截图起停)+ **接缝**(代理完成→主线验证→下一票的空档)。
- 每个大户再切一层内部结构(模型/bash/等待)——「代理慢」多数是「代理在反复跑验证」,对策完全不同。

### 4. 痛点归类(对照分类法;新类型如实标注,不硬塞)

| 类  | 痛点           | 典型信号                              | 既有对策出处                                             |
| --- | -------------- | ------------------------------------- | -------------------------------------------------------- |
| P1  | 等待验证管线   | 主线反复全量 e2e/build                | AGENTS.md「本地 e2e 跑法」分层验证 + 开发与测试.md 命令  |
| P2  | flake 取证     | 同一 spec 反复重跑做定性              | 修测试本体(test.slow/固定 seed);`--repeat-each` 定向三连 |
| P3  | 代理验证密度   | 实现票内大量截图/对比度/跨 spec 回归  | 派单模板「验证限额」                                     |
| P4  | 拆票粒度不对称 | 并行两票墙钟悬殊,快者被遮盖           | 派单模板「拆票检查单」                                   |
| P5  | 接缝串行 QC    | 每道代理缝 3-7min 主线验证            | 底盘(单人单线程物理下限),如实告知不可压                  |
| P6  | 决策往返(HITL) | 多轮一问一答,轮间隙全是用户时间       | 批量提问(向用户提议,如拷问会一次五问)                    |
| P7  | 探索-构建循环  | 一次性调研的 clone/build/run 串行等待 | 外包后台代理(成本收益评估后再立项)                       |
| P8  | 环境/网络重试  | 超时报错、push/API 重试               | 通常小额(<5min),明确说「不值得治理」                     |

### 5. 输出(固定结构)

1. **总账一行**:窗长、轮内耗时、离席(单列)。
2. **分解表**:子代理(可见/被遮盖)/主线模型/等待/接缝,分钟数 + 百分比。
3. **痛点排行**:按可见墙钟降序;每条 = 现象 + 数据证据(次数×分钟)+ 归类(P1-P8)+ 是否已被既有条款覆盖。
4. **推荐方案(依次排序)**:按「可省时间 × 实施成本」排;每条注明是引用既有条款(给出处)还是新提案(给具体动作);给出重演预估(同规模任务按方案执行预计多久)。区分「工程可修」与「结构性/人的带宽」——后者不伪装成可自动化。
5. **入账**:`docs/agents/耗时回顾.md` 末尾基线账表追加一行(列:任务/日期/墙钟/子代理可见与被遮盖/主线 e2e/主线模型/接缝/备注)。**分析完停手,方案落地等用户逐条拍板**。

## 口径红线

- 只计轮内时间;离席剔除但必须单独报。
- 主线程模型时间以 rollout `durationMs` 求和为准;CLI 日志 turn.durationMs 只做交叉印证(口径差几个点属正常)。
- 结论必须带数字(次数 × 分钟),不接受「感觉花了很多时间」式表述。
- 子代理内部必须拆(模型/bash/等待);主线等待必须逐条认领到用途,不留「其他」黑桶。
